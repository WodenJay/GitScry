# Queries incrementally refresh an explicitly initialized cache

Users must run `gitscry index` once before querying a repository; every query command, including `conflicts`, requires an existing compatible, readable, published cache. Once initialized, queries synchronously refresh that cache by default, without a configuration switch. Queries already inspect Git targets and historical coverage, so the earlier cache-only rationale no longer justifies requiring manual refresh after every history change; we accept first-query refresh latency rather than introduce hooks or background process management.

Ordinary queries refresh all locally available history reachable from the HEAD fixed for that invocation, including merged history. Query filters do not narrow maintenance, and explicit revisions do not authorize refreshing unrelated history. `conflicts` shares the refresh lifecycle but targets its fixed ours and theirs histories instead of HEAD alone. Refresh adds missing material while retaining previously cached history; a different published cache tip is not itself a reason to refresh an already covered target. Queries do not fetch remote history, scan all branches, prune, clear, repair, or upgrade the cache. Initial construction and those maintenance operations remain explicit.

Concurrent queries wait for the shared cache lock and recheck what still needs refreshing before writing, avoiding duplicate work. A query does not chase HEAD changes during refresh. There is no default timeout, consistent with ADR-0005; waiting and actual refresh work must expose progress without contaminating JSON stdout.

Refresh failure may fall back to the published cache only when it remains safely readable and satisfies the command's existing query prerequisites. Such results must explicitly report the refresh failure and any incomplete historical coverage in both human and JSON output. Otherwise the query fails rather than returning unrelated material or presenting unavailable history as an empty result. Successful refresh does not imply complete coverage: shallow history and missing local objects must still be disclosed and must not trigger repeated refresh solely because coverage remains incomplete.

Automatic refresh maintains semantic coverage only when semantic indexing was explicitly enabled, and uses local resources without downloading models or runtimes. Semantic maintenance failure does not prevent ordinary historical queries from using safely published history, but must be reported. Hybrid queries whose semantic prerequisites are unmet fail explicitly rather than silently degrading to lexical search. Resource installation and repair remain explicit operations.
